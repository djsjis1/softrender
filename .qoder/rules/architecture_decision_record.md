# 架构决策记录规范

## 核心原则

重要的设计决策必须有书面记录。

半年后没人知道「为什么要这样设计」是不可接受的。

```

├── README.md              # ADR 索引（所有决策的摘要列表）
```

# ADR 必须记录的场景

以下情况必须创建 ADR：

* 引入新的设计模式（如 Command、Observer、Strategy）
* 选择第三方库（如 FFmpeg vs GStreamer）
* 架构分层变更（如引入中间件层）
* 通信协议选择（如 Modbus vs CANopen）
* 数据存储方案（如 SQLite vs 文件系统）
* 跨平台兼容性决策（如 Windows only vs 跨平台）
* 性能关键路径的优化策略
* API / ABI 兼容性取舍

# ADR 模板

每个 ADR 文件命名：`ADR-<三位编号>-<简短描述>.md`

```markdown
# ADR-001：使用命令模式实现时间轴撤销/重做

## 背景

项目需要实现时间轴编辑功能，用户需要：

* 撤销（Undo）上一步操作
* 重做（Redo）已撤销的操作
* 支持多种操作类型（移动、删除、属性修改）

## 问题

如何设计才能支持灵活的撤销/重做，同时保持代码可扩展？

## 备选方案

### 方案 A：状态快照模式

每步操作前保存完整状态快照。

- 优点：实现简单
- 缺点：内存占用大（每帧保存完整状态导致内存爆炸），不适合长时间编辑

### 方案 B：命令模式（Command Pattern）

每步操作封装为 Command 对象，维护 execute/undo 接口。

- 优点：内存高效（只存储操作差异），易于扩展新操作类型
- 缺点：每种操作需实现 execute + undo 两个方法，开发量稍大

## 最终方案

**方案 B：命令模式**

## 选择原因

1. 时间轴可能包含数百步操作，快照模式内存不可接受
2. 命令模式天然支持操作队列，与时间轴数据结构一致
3. 新增操作类型只需新增 Command 子类，符合 OCP 原则

## 影响范围

* 新增 `commands/` 模块目录
* 核心模块：`Command.h`（抽象基类）、`CommandQueue.h`（撤销栈/重做栈）
* 所有用户操作需封装为 Command 子类

## 状态

已采纳（2026-01-12）
```

```markdown
# ADR-007：远程通信协议选择（替代 ADR-005）

## 背景

客户端需要与远程服务通信，服务端可主动推送通知（实时性）。

## 备选方案

- 方案 A：HTTP REST 轮询（ADR-005 原方案）——实时性差，高频轮询浪费带宽
- 方案 B：WebSocket——全双工长连接，有成熟开源库
- 方案 C：自定义 TCP 二进制协议——极致性能但成本过高

## 最终方案

**方案 B：WebSocket**

## 选择原因

1. 服务端推送需求排除 HTTP 轮询（ADR-005 被替代）
2. 有成熟开源库可直接集成
3. 自定义协议成本不划算

## 影响范围

* 新增 `network/` 模块；集成 WebSocket 库到 `third/`
* ADR-005 标记为「已替代」

## 状态

已采纳（2026-03-01）
```

# ADR 管理规则

## 不可修改原则

已采纳的 ADR 不得事后修改内容。

若决策发生变化：

1. 创建新的 ADR 记录新决策
2. 旧 ADR 状态标记为「已替代（见 ADR-XXX）」
3. 更新 `docs/adr/README.md` 索引

禁止：

* 直接修改旧 ADR 内容
* 删除旧 ADR（应保留历史）

## AI 触发规则

AI 在 Step 3（设计方案）时若判断本次变更涉及 ADR 场景，必须：

1. 提醒用户「建议创建 ADR 记录本次决策」
2. 若用户同意，按照模板创建 ADR 文件
3. 更新 README.md 索引
