# 14 · 多线程并行光栅化

> 单线程 CPU 渲染器跑到这里，性能瓶颈已经很明显。好消息是：光栅化天然适合并行——每个像素的着色互不依赖。本篇讲怎么把屏幕切成条、多线程各画各的、最后合并深度。

## 一、为什么光栅化是"embarrassingly parallel"

光栅化的内层循环对每个像素独立做：重心坐标判定 → 深度测试 → 片元着色 → 写颜色。像素之间**没有数据依赖**（不像物理模拟需要邻居信息）。这意味着可以把屏幕切成任意块，分给不同线程，各自跑完再合并。

GPU 之所以快，本质就是把成千上万个像素分给数千个核心同时算。我们在 CPU 上用 `std::thread` 模拟同样的思想。

## 二、分条策略

最简单：**水平分条**。屏幕 H 行分成 N 条（N = 线程数），每条 `[yStart, yEnd)` 交给一个线程。每个线程拥有自己的**局部颜色缓冲 + 局部深度缓冲**，渲染时只写自己条带内的像素——**零竞争、零锁**。

```
Thread 0: rows [0, H/N)
Thread 1: rows [H/N, 2H/N)
...
Thread N-1: rows [(N-1)H/N, H)
```

代码 `examples/stage14_threaded.cpp` 的 `StripBuffer` 就是每条带的局部缓冲。

## 三、深度合并的问题

分条后，每条带只看到"自己那几行"的深度。如果一个三角形跨越两条带的边界，两个线程各自画了自己那部分——**这没问题**，因为深度测试只在同一条带内竞争，跨条带的像素本来就不重叠。

但如果用**按三角形分**而非按像素分（另一种策略），两个线程可能画同一像素，就需要原子操作或合并阶段。本项目选按像素分条，避免了这个复杂性。

## 四、Amdahl 定律与开销

实测中你会发现：场景太简单时，多线程反而**更慢**——因为线程创建/同步的固定开销 > 省下的计算时间。这就是 **Amdahl 定律**的体现：并行只能加速"可并行部分"，而串行开销（线程启动、合并）是固定的。

> 经验法则：每线程至少处理几万个像素的着色，并行才有正收益。800×600 = 48 万像素，12 线程每线程 4 万像素——对简单场景刚好在临界点附近。加更多三角形或更重的片元着色（如 PBR），加速比会显著上升。

## 五、对应代码

| 概念 | 代码 |

## 六、动手实验

1. 把球体数从 20 加到 200，或把分辨率提到 1920×1080，再看加速比——负载重了，并行收益就出来了。
2. 把 `numThreads` 强制设 1，对比多线程=1 和单线程路径的耗时（应该几乎相同，验证正确性）。
3. 尝试**按三角形分**而非按行分：每个线程画全部三角形但只写 `threadId % N == y % N` 的行。观察是否需要原子深度操作。

## 七、小结

- 光栅化逐像素独立，天然并行。
- **水平分条**：每线程一条带 + 局部深度，零锁零竞争。
- 场景太轻时线程开销 > 收益（Amdahl 定律）。
- GPU 的数千核心本质就是"极细粒度的像素并行"。
