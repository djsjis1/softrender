# 28 · 第三方库管理策略

> 企业级项目必须有清晰的第三方库管理规则：放哪、怎么集成、谁负责更新、渲染器本体是否依赖。本篇总结本项目的策略。

## 一、核心原则

1. **核心光栅化与数学（`include/softrenderer/math/`、`render/raster/`）零第三方依赖**——纯 C++23 标准库，任何平台编译即用。其余模块（图像加载、glTF、ECS）依赖仓库内置第三方代码，完整说明见 [architecture.md](../architecture.md)。
2. **第三方库源码放在 `third/`**——不要求用户手动安装，`add_subdirectory` 一键集成。
3. **使用层（examples/）可选依赖**——通过 CMake option 控制是否启用。
4. **版本锁定**——`third/` 里放的是确定版本的源码快照，不用 git submodule（避免网络依赖）。

## 二、当前第三方库

| 库 | 路径 | 用途 | 集成方式 |
| --- | --- | --- | --- |
| Google Test 1.15 | `third/googletest-main/` | 单元测试 | `add_subdirectory` + `EXCLUDE_FROM_ALL` |
| spdlog 1.17 | `third/log/spdlog-1.17.0/` | 日志 | 通过 `third/log/CMakeLists.txt` 封装 |

## 三、添加新库的流程

1. 下载源码快照到 `third/<lib-name>/`
2. 编写或复用其 `CMakeLists.txt`（确保支持 `add_subdirectory`）
3. 在主 `CMakeLists.txt` 加 `option(SR_ENABLE_XXX ...)` + `add_subdirectory`
4. 提供 `sr_enable_xxx(target)` 辅助函数
5. 渲染器本体通过条件编译（`#ifdef SR_USE_XXX`）可选使用
6. 更新本文档

## 四、为什么不 git submodule

- CI 环境可能无网络
- submodule 更新不可控（上游 force push 会破坏构建）
- 源码快照 = 构建可复现性

代价是更新时需要手动替换目录。对于渲染器这种低频依赖更新的场景，完全可接受。
